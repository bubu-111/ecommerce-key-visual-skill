# 通用评估与迭代

基准来自当前用户任务与原始资料，而非某个固定商品案例。先列必需字段、素材、设计约束和传播目标，冻结版本后测试。准确性测试固定同一套参考基准（同一份素材与同一份需求原文），避免只凭对上一版的印象判断。

| 维度 | 方法 | 证据 |
| --- | --- | --- |
| 准确性 | 相同基准多次独立运行，并分两步核对：①**核对内容**——提取、归纳、文案与合成约束是否准确；②**核对执行**——流程是否按预期走完，是否暴露出原资料中说不清、互相矛盾或缺少依据的地方 | 输入来源、漏项/错误/无依据新增、成图；流程中卡住或需要临时判断的节点；DOM 检查不能替代视觉检查 |
| 稳定性 | 同义表达保持任务不变（区分"同义改写"与"任务已变化"）；另测支持环境与字体变化，把"能调用"与"能稳定完成"分开看 | 意图、流程、关键字段和交付；任务变化另记 |
| 质量性 | **先做一轮精简**（合并重复、删掉可由其他条目推出的复述），**逐条核对 `SKILL.md` 核心规则的各条是否仍有对应写法——这份「核心规则各条」即本项所说的核心能力清单**，再以同输入/模型/环境比较版本与成本 | 事实和素材覆盖、独立视觉评审、完成率、行数/字符数/Token/耗时/调用/返工 |
| 实用性 | 由未参与编写者独立执行并改稿；输入要覆盖**正向要求、异常要求、边界情况与复杂链路**（含范围外要求应被正确拒绝） | 六项评审：理解／执行／质量／体验／稳定／迁移；记录具体障碍并交回作者复测，附复测结论 |

同伴互换 Skill 是组织上述四类测试的推荐形式之一——它的目的就是检验稳定性、准确性、质量性和实用性，并非四类之外的另一个项目。没有同伴时，可用无编写记忆的独立执行者代理，同样属有效证据，但要如实注明测试形式与范围。

先分别评估信息准确、文件规格和视觉质量，不用单项通过证明全体达标。**成图本身好不好（审美、层级、素材合成）按 `references/quality-rubric.md` 的 1–5 分表评**，分数须有理由和评审者；未评不造分。本文件管的是"这个 Skill 测得对不对"，那份管的是"这张图好不好"，两者都要做。

行数区分主文件、参考文档、模板和脚本；挪文件或压缩换行不自动等于成本降低。质量性先冻结基线版本，再比较改前改后。重导出不算独立任务重复运行；反馈复查不等于同伴从零执行。不可获取的指标写未知；报告只覆盖已测部分，不宣称未测能力。

| 版本/日期 | 输入与测试条件 | 现象/证据 | 原因与改动 | 复测结果 | 待测范围 |
| --- | --- | --- | --- | --- | --- |

每次修改先复测原失败用例，再回归关键能力；记录旧版失败与新版结果。案例用于发现可迁移问题，产品名称、参数、配色、卖点数量、语种和比例不应写成通用规则。规则增加的价值须由真实输出和成本比较证明。

## 迭代记录的口径（四处最容易填错）

**① 「次生错误」不许一律填 0。** 次生错误＝"修完一处之后，有没有回头检查它没直接影响到的其它元素"。没做这次回归检查的，**填「未评估」而不是 0**；一律填 0 会得出"修复从不引发新问题"的假结论（经验上约三分之一的问题是修复动作的连锁产物）。建议把这一栏拆成两列：「已发现并修复的连锁问题」＋「未做回归检查的项数」。

**② 分数与缺陷数不能只由执行者自报。** 五维评分、缺陷个数、迭代轮次若全部来自干活的执行者，视为**自评**，须在记录里标明"自评"；并另加一次独立复核（换一个执行者，或作者按同一评分标准重打一遍）。能自动化的项优先固化成脚本：

| 指标 | 怎么判定 | 参考实现 |
| --- | --- | --- |
| 尺寸 / 格式 | 读图片文件头 + 像素尺寸 | `scripts/png-check.cjs` |
| 超画布 / 裁字 | 元素矩形 vs 画布矩形 | `scripts/layout-audit.cjs`（报出溢出像素数） |
| 商品在画面里占多大 | 用商品专属色取最大连通域的包围盒 | 需自写脚本（基准校准后才可用） |
| 英文版有没有混中文 | 扫英文版文案 / 图像识别 | 人工目视 |
| 各语种版本号是否同步 | 比对交付文件名 | 人工点出 |
| 方向有没有绑定不同骨架 | 查方案文档 | 人工比对 |

**③ 连续型指标必须配同条件的对照跑。** 同一份技能包、同一份输入，跑两遍结果也可能差很多（实测同一份冻结版，商品渲染高度 308–496px）。因此：

- **"看不出差别"的模块只能写「未观察到稳定差异」，不能写「该模块无用」**；
- 优先采用「是 / 否」「数个数」这类离散指标，少用"量出来是多少"这类连续指标；
- **对照基准必须与实验组同条件**（如另设"同环境 ＋ 完整版"的控制跑）。若拿"有反馈、有上下文"的历史轮次当对照，条件不同，只能作**基准行**，不作**实验对照**。

**④ 凡是"改动了被规范的载体文件"的结论，必须回到文件层面核验。** 执行者自述"我改了模板 / 脚本"时，须对该文件做哈希比对（与冻结版逐字节比），确认改的是**受规范的载体文件**还是**它自己的产出**——两者性质完全不同，不可混算，也不能直接采信自述。
